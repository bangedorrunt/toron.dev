The bug. components/docs-content.tsx rendered the callout body inside a <p>. MDX wraps
the body of a JSX block in a paragraph of its own, so .next/server/app/docs.html served

  <div class="toron-callout"><p class="toron-callout__glyph" aria-hidden="true">↻</p>
  <div><h3>Which plane do I need?</h3><p><p>Start with the failure you actually have. …
  </p></p></div></div>

A <p> start tag closes an open <p> first, so the parser produced two siblings — an empty
<p> and the text <p> — where React renders a parent and a child. React reported #418 and
regenerated the whole tree on the client, on every docs page carrying a callout.

The route list is what found it. Against a production build, these log #418: /docs,
/docs/toron, /docs/beads, /docs/flywheel, /docs/chiebukuro, /docs/guides,
/docs/guides/crash-recovery. These log none: /docs/guides/close-with-evidence,
/docs/guides/first-signed-handoff, /docs/guides/remember-and-recall,
/docs/guides/toron/session-door, /docs/guides/beads/cli-reference. The failing set is
exactly the pages whose MDX carries a Callout, and the served markup at that component
showed the nesting immediately.

Fixed by rendering the body as a div with its own class, and moving the css hook with it.
The old rule was `.toron-callout p:last-child`, which had been matching the paragraph MDX
made rather than the one the component wrote — the parser's fixup had already turned the
component's own <p> into an empty sibling, so the styling worked by accident.

After the fix, every route above logs no React error. The only console error left on any
page, off Vercel, is the 404 for /_vercel/insights/script.js, which Vercel serves.

Guards added to the harness, because this bug's only symptom is a console message:

  valid nesting    every built page's HTML (110 of them) is scanned for a block element
                   inside a <p>. The predicate is proved both ways: it flags the pre-fix
                   markup string and not the post-fix one.
  no page errors   /docs and /docs/guides are loaded for their console on every run.
                   Nothing sampled page errors before, which is why this survived.
  callout body     the body's tag is read off that same load, with the computed margin of
                   its paragraph, so a re-nesting that silently dropped the styling would
                   fail rather than pass.

Correction, recorded because the bead's description said otherwise: "dev mode is clean" was
an artifact. The dev client in that probe run never booted (the HMR websocket handshake
failed), so nothing hydrated and nothing was reported. The malformed markup is served
identically in dev and production. What changes between the two is only whether a listener
is watching.

The instrument that did not work is worth keeping too: comparing the served HTML against
the DOM after hydration finds nothing, because React's recovery render is the client's
version of the tree and it leaves both sides agreeing. The comparison that did work was
between the routes that fail and the components they share.
